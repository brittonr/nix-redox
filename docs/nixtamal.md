# Building without flakes (Nixtamal)

The flake is the primary interface. `default.nix` and `shell.nix` evaluate the
same flake outputs without the `flakes` experimental feature, with every input
pinned by [Nixtamal](https://nixtamal.toast.al/) in `nix/tamal/`. The
derivations are identical to the flake's, so build results and the binary
cache are shared between the two.

## Use

Attribute paths are the flake's output paths: `nix build .#diskImage` becomes
`nix-build -A packages.x86_64-linux.diskImage`.

```bash
nix-build                                        # graphical disk image (packages.<system>.default)
nix-build -A packages.x86_64-linux.diskImage     # development image without graphics
nix-build -A checks.x86_64-linux.tier-eval       # fast checks
nix-shell                                        # devShells.default; also -A native, -A minimal
```

Apps are scripts in packages; build the package behind the app and run it:

```bash
nix-build -A packages.x86_64-linux.run-redox-graphical-desktop
./result/bin/run-redox-graphical                 # nix run .
nix-build -A packages.x86_64-linux.run-redox-default
./result/bin/run-redox-cloud-hypervisor          # nix run .#headless
```

Besides the [quick start](../README.md#quick-start)'s host requirements, minus
flakes:

- `git` on `PATH`: Redox GitLab inputs are fetched with `builtins.fetchGit`
  during evaluation.
- The flake's `nixConfig` does not apply, so configure the
  [binary cache](binary-cache.md) yourself (`cachix use nix-redox`).

With direnv, `use nix` in `.envrc` loads `shell.nix`.

## How it works

- `nix/tamal/manifest.kdl` has one input per `flake.lock` node, named after the
  node. Each fresh-cmd prints that node's revision from `flake.lock`, so
  `flake.lock` remains the single source of truth for revisions.
- Inputs are fetched at evaluation time under the store name `source`, as flake
  inputs are. They land at the flake's store paths, which keeps every
  derivation identical.
- `nix/nixtamal.nix` wires the pins together along `flake.lock`'s graph,
  including `follows`, and calls each flake's `outputs`, as flake-compat does.
  The repository itself is `builtins.fetchGit` of the checkout: tracked files
  plus their uncommitted edits, like a flake's `self`. Untracked files are left
  out, so `git add` new files before building.
- Redox GitLab inputs use Nixtamal's `git` kind. The archive endpoint that flake
  `gitlab:` inputs download answers non-browser clients with a challenge page
  (HTTP 403, observed on 2026-11-13), while Git over HTTPS works.
- `nix/tamal/lock.json` and `nix/tamal/default.nix` are generated by
  `nixtamal lock`; do not edit them.

GitHub archive pins carry no revision or timestamp metadata, so
`inputs.<name>.rev` and the suffix of `inputs.nixpkgs.lib.version` differ from
the flake. Nothing in this repository reads them.

## Keeping the pins in sync

The `nixtamal-pins` check (eval tier) fails while `nix/tamal/lock.json` and
`flake.lock` pin different sources, and CI checks that `default.nix` evaluates
`checks.x86_64-linux.tier-eval` to the flake's derivation. Run Nixtamal 3.0 or
newer from the repository root, with `jq` on `PATH`.

After `nix flake update` or any other `flake.lock` change:

```bash
nixtamal refresh
nix build .#checks.x86_64-linux.nixtamal-pins
```

For a new `flake.lock` node, add an input with the node's name to
`manifest.kdl` (copy a neighbour: GitHub inputs use `archive`,
`gitlab.redox-os.org` inputs use `git`), then run `nixtamal lock <name>`. Delete
the inputs of removed nodes and run `nixtamal lock`.

The release tarballs `openssl3-src` and `openssh-src` are `frozen`, so
`nixtamal refresh` skips them. When their URL changes in `flake.nix`, change it
in `manifest.kdl` too and run `nixtamal lock <name>`.

## Running Nixtamal on Redox

Development images include upstream Nixtamal 3.1.0, Git, curl, and Snix's
native `nix`, `nix-hash`, `nix-prefetch-url`, `nix-prefetch-git`,
`nix-instantiate`, and `nix-store` compatibility commands. These commands
implement the operations Nixtamal needs, not the entire Nix CLI.

The CLI embeds portable OCaml bytecode in a Redox executable, linked against
the matching OCaml 5.4 runtime, relibc, and target C bindings. The compiler and
PPX generators run on the build host; no Linux executable runs in the guest.
Camomile's Unicode tables and dependency notices are bundled with the guest
package. Git's POSIX helper command strings use the installed Bash, not Ion;
its private helper binaries and templates are retained in the image.
The package pins Nixtamal's newer dependency package set because it needs
Eio 1.6 rather than the main package set's Eio 1.3.

Build the guest executable without flakes:

```bash
nix-build -A packages.x86_64-linux.nixtamal
```

For a project's native manifest, use `default-fetch-time eval` and
`default-hash-algorithm SHA-256` with archive or Git inputs. SHA-256 keeps Git
prefetch results and the generated loader's `builtins.fetchGit` at the same
canonical store path. Other VCS prefetchers are not bundled; any programs
used by `fresh-cmd` must also be installed in the guest.

From that project's root inside Redox:

```bash
nixtamal lock --directory ./nix/tamal --jobs 1 --no-tui
nixtamal refresh --directory ./nix/tamal --jobs 1 --no-tui
snix eval --expr 'import ./nix/tamal { bootstrap-pkgs = {}; }'
```

For Nixtamal's experimental generation roots, set
`NIXTAMAL_EXPERIMENTAL_GC=1` and use `default-gc track` in the manifest.
`NIXTAMAL_GC_GENERATIONS=0` retains all generations. Snix registers real
content-addressed store objects and indirect GC roots; it does not fabricate
store paths or report success for missing inputs.

The isolated offline VM proof uses the actual upstream CLI to lock local
archives and immutable Git inputs whose branch HEAD has advanced. It evaluates
the generated loader, preserves an existing pin on a second lock, refreshes to
different archive contents, and validates both generations' contents and store
registration. It does not run global store GC:

```bash
nix-build -A packages.x86_64-linux.nixtamal-test
./result/bin/functional-test --verbose
```

### Git fetch behavior

Fixed commit IDs clone advertised history; named refs remain shallow. This
can fetch more history, but works with older servers that reject direct
requests for unadvertised ancestor commits.
